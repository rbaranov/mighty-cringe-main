# Mighty & Cringe — инструкции для работы с проектом

## О продукте

Mighty & Cringe — русскоязычная offline-first PWA для личного учёта силовых тренировок.
Главная ценность: спортсмен быстро и надёжно фиксирует то, что действительно сделал в
зале, а затем видит собственный прогресс. Голосовой ввод, AI-разбор и доступ тренера —
последующие возможности, а не причина ухудшить ручной сценарий.

Технологии и границы:

- `apps/web` — React PWA и локальное хранилище IndexedDB.
- `apps/api` — Fastify API и граница авторизации.
- `apps/worker` — будущая асинхронная обработка голоса, уведомлений и повторов.
- `packages/contracts` — доменные типы и API-контракты.
- `packages/db` — PostgreSQL и миграции Drizzle.
- `infra/production` — Docker Compose и Caddy.
- Production: `mightycringe.com`, Hetzner Helsinki, Caddy, private PostgreSQL network,
  GitHub Actions self-hosted runner.

## Статус и границы безопасности

- Текущий сайт — технический preview. В нём нет настоящей авторизации: фронтенд и API
  используют демонстрационного пользователя. Не хранить реальные персональные или
  голосовые данные до завершения OAuth и проверенных автоматических бэкапов.
- Object Storage ещё не создан; аудио не загружается, worker не обрабатывает голос или push.
- Никогда не добавлять в репозиторий пароли, OAuth client secret, S3 key, приватные SSH-ключи
  или содержимое production environment file.
- Пока P0-задача CI/CD не завершена, production-деплой запускать только вручную через существующий GitHub Actions workflow. На сервере использовать пользователя `deploy`, не root.

## Источники правды

- `docs/BACKLOG.md` — весь незавершённый пользовательский бэклог. Список упорядочен;
  сначала раздел «Актуальное», затем «Потом».
- `docs/DONE.md` — только завершённые инкременты и фактически выполненные работы.
- `docs/product/` — исходное описание продукта и интерактивные mockups.
- `docs/adr/` — архитектурные решения.
- `docs/deployment/` и `infra/production/` — инструкции по эксплуатации production.

## Правила ведения работы

1. Перед новой существенной задачей прочитать этот файл, `docs/BACKLOG.md`, `docs/DONE.md`
   и относящийся к задаче ADR/runbook.
2. Формулировать и реализовывать работу через пользу спортсмену. Новая задача должна иметь
   пользовательский результат и проверяемый критерий готовности.
3. После выполнения задачи обновить документацию в том же изменении: убрать задачу из
   `docs/BACKLOG.md`, добавить краткий факт в `docs/DONE.md`, если задача полностью завершена.
   Если работа частичная, уточнить её формулировку и порядок в бэклоге, не переносить в DONE.
4. Все доработки выполнять в отдельной ветке от `main`, обычно с именем
   `agent/<краткое-описание>`; не коммитить доработки прямо в `main`.
5. После изменений предлагать пользователю merge ветки в `main`. Выполнять merge только после
   явного разрешения пользователя.
6. После каждой выполненной задачи в финальном сообщении обязательно давать ссылки на
   `docs/BACKLOG.md` и `docs/DONE.md`.
7. Не выдавать технический preview за готовый пользовательский production. Перед изменением
   production проверять, не затрагивает ли оно данные, доступ, DNS, секреты или возможность
   восстановления.

## Проверка изменений

- Для кода запускать релевантные тесты, typecheck и/или сборку из `package.json`.
- Для изменения инфраструктуры проверять конфигурацию и health endpoint после деплоя.
- Не считать изменение готовым, если в документации осталось противоречие фактическому
  состоянию приложения или production.
