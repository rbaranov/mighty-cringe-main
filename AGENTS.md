# MightyCringe — инструкции для работы с проектом

## О продукте

MightyCringe — русскоязычная offline-first PWA для личного учёта силовых тренировок.
Главная ценность: спортсмен быстро и надёжно фиксирует то, что действительно сделал в
зале, а затем видит собственный прогресс. Голосовой ввод, AI-разбор и доступ тренера —
последующие возможности, а не причина ухудшить ручной сценарий.

Технологии и границы:

- `apps/web` — React PWA и локальное хранилище IndexedDB.
- `apps/api` — Fastify API и граница авторизации.
- `apps/worker` — асинхронная обработка голоса, будущих уведомлений и повторов.
- `packages/contracts` — доменные типы и API-контракты.
- `packages/db` — PostgreSQL и миграции Drizzle.
- `infra/production` — Docker Compose и Caddy.
- Production: `mightycringe.com`, Hetzner Helsinki, Caddy, private PostgreSQL network,
  GitHub Actions self-hosted runner.

## Статус и границы безопасности

- Google OAuth настроен в production; владелец проверил вход, выход и изоляцию данных двух аккаунтов.
  Не хранить реальные персональные или голосовые данные до настройки и проверки автоматических
  бэкапов.
- Отдельный Object Storage для голоса ещё не настроен. Голосовой код должен оставаться выключенным,
  пока нет private bucket, ограниченных S3 credentials, SSE-C recovery key и приватного OpenRouter
  ключа; не переиспользовать bucket или credentials бэкапов.
- Никогда не добавлять в репозиторий пароли, OAuth client secret, S3 key, VAPID private key,
  приватные SSH-ключи или содержимое production environment file.
- Изменения автоматически попадают в production только после успешного CI на `main`.
  Ручной запуск `Deploy production` использовать для контролируемого повторного деплоя
  текущего `main`. На сервере использовать пользователя `deploy`, не root.

## Источники правды

- `docs/BACKLOG.md` — весь незавершённый пользовательский бэклог. Сначала идут «В работе» и два
  приоритизированных трека «Продуктовые» / «Технические», затем отдельные блоки «Ждёт владельца» и
  «Позже». Выпущенный код, PR и отчёты CI сюда не дублируются.
- `docs/DONE.md` — только завершённые инкременты и фактически выполненные работы.
- `docs/product/` — исходное описание продукта и интерактивные mockups.
- `docs/adr/` — архитектурные решения.
- `docs/deployment/` и `infra/production/` — инструкции по эксплуатации production.

## Правила ведения работы

1. Перед новой существенной задачей прочитать этот файл, `docs/BACKLOG.md`, `docs/DONE.md`
   и относящийся к задаче ADR/runbook.
2. Формулировать и реализовывать работу через пользу спортсмену. Новая задача должна иметь
   пользовательский результат и проверяемый критерий готовности.
3. После выполнения задачи обновить документацию в том же изменении: убрать задачу из
   `docs/BACKLOG.md`, добавить краткий факт в `docs/DONE.md`, если задача полностью завершена.
   Если работа частичная, коротко обновить её состояние в «В работе». Если код выпущен, но нужны
   credentials или acceptance владельца, оставить в «Ждёт владельца» только конкретное действие —
   без повторного описания реализации и CI.
4. Все доработки выполнять в отдельной ветке от `main`, обычно с именем
   `agent/<краткое-описание>`; не коммитить доработки прямо в `main`.
5. Перед предложением merge подготовить ветку к локальной проверке владельцем: дать точные команды
   запуска и краткий сценарий acceptance-проверки для сделанного изменения. CI, автоматические
   тесты и проверка агента не заменяют эту локальную проверку.
6. Выполнять merge в `main` только после того, как владелец явно сообщил, что локальная проверка
   пройдена, и явно разрешил merge. Одно однозначное сообщение вроде «локально проверил, мержи»
   удовлетворяет обоим условиям. Если владелец не может проверить изменение, оставить ветку
   несмерженной, отметить блокировку в `docs/BACKLOG.md` и перейти к следующей независимой задаче.
7. После успешного merge в `main` удалить рабочую ветку и из GitHub, и из локального
   репозитория, предварительно убедившись, что PR отмечен как merged и изменения присутствуют
   в `main`. Не удалять `main` и другие защищённые или долгоживущие ветки.
8. После каждой выполненной задачи в финальном сообщении обязательно давать ссылки на
   `docs/BACKLOG.md` и `docs/DONE.md`.
9. Не выдавать технический preview за готовый пользовательский production. Перед изменением
   production проверять, не затрагивает ли оно данные, доступ, DNS, секреты или возможность
   восстановления.
10. На рабочем Mac GitHub credentials хранятся в системном macOS Keychain через `osxkeychain`.
    Сообщение `gh auth status` о недействительной сессии не означает, что credential в Keychain
    отсутствует: сначала получить токен командой `gh auth token -h github.com`, обязательно
    перехватив stdout прямо во временную task-specific shell-переменную, и проверить его через
    `GH_TOKEN="$task_specific_token" gh api user`. Не запускать `gh auth token` без перехвата
    вывода, не печатать токен и не сохранять его в файлах, конфигурации shell или репозитории.
    Для всех последующих `gh`-команд передавать этот токен только во временном `GH_TOKEN` того же
    процесса. Если этот способ не сработал, использовать `git credential fill` с явным
    `osxkeychain`, обходя GitHub-specific helper `gh auth git-credential`, который может скрывать
    рабочую запись Keychain. Просить владельца повторно входить в GitHub только после того, как оба
    способа действительно не предоставили рабочий credential.
11. После выполнения каждой задачи всегда запускать приложение локально из актуальной рабочей
    ветки и оставлять его доступным на время acceptance-проверки владельца. Перед финальным
    сообщением проверить, что web-интерфейс и локальный health endpoint отвечают, а в финальном
    сообщении дать активную Markdown-гиперссылку на фактический локальный адрес приложения.
    Команды запуска и сценарий проверки дополняют ссылку, но не заменяют её. Если локальный запуск
    невозможен, не считать задачу готовой: явно описать блокировку и зафиксировать её в бэклоге.

## Проверка изменений

- Для кода запускать релевантные тесты, typecheck и/или сборку из `package.json`.
- Для изменения инфраструктуры проверять конфигурацию и health endpoint после деплоя.
- Не считать изменение готовым, если в документации осталось противоречие фактическому
  состоянию приложения или production.
